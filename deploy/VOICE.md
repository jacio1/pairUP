# Голосовые комнаты PairUp

## Архитектура

Браузер → POST `/api/rooms/:id/voice/token` → NestJS проверяет cookie и доступ к комнате → JWT на 120 секунд → браузер подключается непосредственно к LiveKit SFU.
Аудио не проходит через NestJS, Socket.IO и PostgreSQL. Схема БД не меняется.
Токен разрешает подписку и публикацию только микрофона в одной комнате. API secret остаётся на сервере. Ответ endpoint не кешируется; выдача ограничена 12 запросами в минуту на сессию (локальный лимитер, при нескольких API-узлах заменить общим).

Подключение слушателем, включение микрофона отдельным действием, mute/unmute, участники и активный говорящий, восстановление соединения средствами SDK. При выходе из комнаты/аккаунта снимаются обработчики, закрывается соединение и освобождается микрофон. Ошибки аудио не блокируют сообщения. Записи звонков нет.

Одна identity на браузерную сессию: подключение из второй вкладки заменит первое, а не создаст аудиоэхо. Разные TEST-сессии имеют разные identity. JWT ограничивает вход, а не длительность звонка: клиент дополнительно выходит по истечении авторизации. Для принудительного отзыва уже активных соединений в будущем нужен серверный RemoveParticipant при отзыве сессии; сам по себе logout в другой вкладке немедленного отзыва медиа не обеспечивает.

## Локальный запуск

1. Запустить Docker Desktop.
2. Из корня: `docker compose -f compose.voice.yaml up -d`.
3. В `server/.env` добавить:

```dotenv
LIVEKIT_URL=ws://localhost:7880
LIVEKIT_API_KEY=devkey
LIVEKIT_API_SECRET=secret
```

4. Перезапустить NestJS и frontend обычными `npm run dev` в соответствующих папках.
5. Войти двумя браузерами/профилями TEST, открыть English → чат → «Подключиться», затем включить микрофон. Использовать наушники.

Конфигурация локальная: рекламируется 127.0.0.1, телефон по Wi-Fi так не подключится. Микрофон доступен на localhost или HTTPS. Нельзя выставлять devkey/secret в интернет.

## Публичный запуск

Можно использовать свой LiveKit или совместимый LiveKit Cloud без изменений frontend. В корневом `.env` установить публичный `LIVEKIT_URL=wss://voice.example.ru` и одинаковые API key/secret у NestJS и LiveKit. Пересоздать server-контейнер. URL должен быть доступен браузерам, а не только внутри Docker.

В `deploy/voice` подготовлен шаблон для отдельного Linux-медиасервера с публичным IP: скопировать туда `.env` с `VOICE_DOMAIN`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` (случайный секрет от 32 символов), создать DNS A на IP, выполнить `docker compose up -d`. Не запускать этот шаблон рядом с текущим Caddy на том же IP: оба занимают 80/443. Для одного VPS объединить конфигурации Caddy и сети вручную после выбора хостинга.

Открыть TCP 80/443 (HTTPS), TCP 7881 (ICE fallback), UDP 7882 (UDP mux). Не публиковать Redis6379 и API7880. Шаблон использует host network, автоматическое определение внешнего IP и максимум 50 участников комнаты. Это стартовая конфигурация, не подтверждённая нагрузочная ёмкость.

Для сетей, блокирующих прямой UDP/TCP, перед публичным показом настроить TURN/TLS443 на отдельном IP/балансировщике или использовать облачный сервис с TURN. В шаблоне TURN не включён: обычный HTTP reverse proxy его не заменяет. Проверить мобильную сеть и Wi-Fi учебного заведения; одного успешного localhost-звонка недостаточно.

## Масштабирование

1. Собирать CPU, память, исходящий трафик, потери пакетов, jitter, RTT, число участников/комнат, ошибки ICE и время подключения.
2. Разнести web/API, PostgreSQL, AI worker и медиасерверы. Секреты доставлять через менеджер секретов; ограничить публикацию аудио, API rate limit сделать распределённым.
3. Добавить LiveKit-узлы на разных VM с общим приватным Redis (HA, ACL/TLS), одинаковыми ключами, доступными публичными ICE-адресами и балансировщиком WSS. Локальный Redis шаблона заменить общей инфраструктурой.
4. Распределение идёт между комнатами: одна комната должна помещаться на одном SFU-узле. При обновлениях использовать drain, а не обрывать активные звонки.
5. Проводить отдельные нагрузочные испытания аудио: число одновременных говорящих и подписок определяет трафик сильнее общего числа открытых страниц. 100 тысяч подключений сайта не означает 100 тысяч голосовых участников. Такая ёмкость здесь не проверялась и требует отдельного расчёта бюджета и кластера.

Документация: [распределённый LiveKit](https://docs.livekit.io/transport/self-hosting/distributed/), [порты и TURN](https://docs.livekit.io/transport/self-hosting/ports-firewall/), [JWT permissions](https://docs.livekit.io/home/server/generating-tokens).

## Проверки

`npm test --prefix server` проверяет права перед выдачей токена, подпись, срок, ограничения комнаты/микрофона, недоступную конфигурацию и совпадение ключей RU/EN.

При запущенном локальном LiveKit: `npm run test:voice --prefix tools` — два браузера с синтетическим микрофоном, проверка получения настоящих RTP-пакетов, mute и выход. `npm run test:voice-ui --prefix tools` дополнительно проверяет настоящий интерфейс Next.js на localhost:3000 с изолированными API-фикстурами, в десктопном и мобильном viewport. Тесты удаляют только собственные случайно именованные медиа-комнаты, не пишут в БД и не очищают чаты. Нужен установленный Edge.

Оба сценария пройдены локально на Windows с LiveKit 1.13.11. Реальный микрофон/динамики, TURN, публичное развёртывание, переподключение при смене сети и нагрузка требуют репетиции на целевой инфраструктуре.
